# Better Auth のセッションのクッキーキャッシュを 5 分にする

Better Auth の `session.cookieCache` を有効にし、保存する期間（`maxAge`）を 5 分、形式（`strategy`）を `compact` にする。ログインが必要な API へのリクエストのたびに DB を読まないためである。その代わり、ログアウト、セッションの取り消し、利用停止が、ほかの端末で効くまでに最大 5 分かかる。

## 前提

- ログインが必要な API は、リクエストのたびにセッションを確かめる（`apps/api/src/middleware/session.ts` の `auth.api.getSession()`）。
- クッキーキャッシュが無い場合、`getSession()` はリクエストのたびに DB の `sessions` テーブルを読む。DB（Turso）にはネットワークを通して接続する。
- 設計ドキュメントは、セッションのクッキーキャッシュで DB の参照を減らすと定めている。

## 理由

- クッキーキャッシュを有効にすると、Better Auth はセッションとユーザーのデータを署名付きのクッキーに保存する。`maxAge` の間は、`getSession()` は DB を読まずにこのクッキーからデータを返す（Better Auth の Session Management のドキュメント、https://www.better-auth.com/docs/concepts/session-management ）。
- 期間を長くするほど DB を読む回数は減るが、取り消しが効くまでの時間は長くなる。Better Auth のドキュメントの例と同じ 5 分にした。
- 形式は `compact` にした。Better Auth のドキュメントによると、3 つの形式のうちクッキーが最も小さく、処理が最も速い。`compact` は署名するだけで暗号化はしないので、クッキーの中身はブラウザで読める。中身はログインしているユーザー本人のデータなので、本人に読まれても問題は無いと判断した。

## 検討した他の案

- **クッキーキャッシュを使わない**：取り消しはすぐに効くが、ログインが必要な API へのリクエストのたびに DB を読むので、採用しない。
- **期間を 60 秒など短くする**：取り消しが効くまでの時間は短くなるが、DB を読む回数が増える。今は 5 分の遅れを許すことにした。
- **形式を `jwe`（暗号化）にする**：中身は読めなくなるが、クッキーが最も大きくなる。中身を本人から隠す必要が無いので、採用しない。

## この決定による影響

- ある端末でログアウトしても、ほかの端末では最大 5 分間ログインしたままになる。セッションを取り消した場合も同じである。
- 利用停止にしたユーザーも、最大 5 分間は API を使える。セッションのミドルウェアは `suspendedAt` を確かめるが、クッキーキャッシュの間は、キャッシュした時点の値を見るからである。ただし、利用停止にした後の新しいログインは、セッションを作る前に DB を確かめるので、すぐに拒否される（`apps/api/src/auth.ts` の `databaseHooks.session.create.before`）。
- 5 分の遅れを許せない処理（退会など）では、`getSession()` に `disableCookieCache: true` を指定して、DB を読む。
- この 5 分の遅れは、Better Auth のドキュメントの記載から導いたものであり、実際に確かめてはいない（2026-11-16 時点）。
