# プロフィールの変更は自前の API だけで受け付け、お気に入りは一覧ごと置き換える

表示名と自己紹介の変更は `PATCH /api/me` だけで受け付け、Better Auth の `/update-user` と `/change-email` は使えないようにする。お気に入りの曲は、`PUT /api/me/favorite-songs` で一覧ごと置き換える。入力を検証する場所を 1 か所にするためと、並び替え・追加・削除を 1 つの操作で扱うためである。

## 前提

- Better Auth は、ログイン中のユーザーが自分の表示名と画像を変える API（`/api/auth/update-user`）と、メールアドレスを変える API（`/api/auth/change-email`）を、既定で公開している。
- 表示名の上限（`USER_NAME_MAX`）と自己紹介の上限（`USER_BIO_MAX`）は、ADR 0012 のとおり、drizzle のテーブル定義（`text({ length })` と CHECK 制約）に書いている。
- 表示名は、新規登録のときに Google のプロフィールの名前から作られる。
- お気に入りは、曲とアーティストがそれぞれ 10 件まで（`FAVORITE_LIMIT`）で、利用者が並び順を決める。

## 理由

### 1. 変更の入口が 2 つあると、検証の規則が 2 か所に分かれる

- Better Auth の `/update-user` を有効なままにすると、表示名は、`PATCH /api/me` の検証（前後の空白の除去、空の禁止）を通らずに変えられる。DB の CHECK 制約は長さしか確かめない。
- このサービスは画像を使わず、メールアドレスは Google のアカウントのものを使うので、Better Auth のこれらの API は必要ない。

### 2. 一覧ごと置き換えると、並び順と件数の上限を 1 回の検証で確かめられる

- 1 件ずつ追加・削除・並び替えする API にすると、並び順の詰め直しと件数の上限の確認が、操作ごとに必要になる。
- 一覧ごと置き換える形では、入力の配列の長さで件数の上限を、配列の順で並び順を決められる。削除と追加は 1 つの batch（トランザクション）で行うので、途中で失敗しても元の一覧が残る。

## 実装

- `apps/api/src/auth/auth.ts`
  - `disabledPaths: ["/update-user", "/change-email"]`。
  - `databaseHooks.user.create.before` で、登録時の表示名を `toDisplayName`（`apps/api/src/users/display-name.ts`）に通す。前後の空白を除いて `USER_NAME_MAX` 文字で切り、空なら仮の名前にする。Google の名前が CHECK 制約を満たさなくても、登録が失敗しないようにするためである。
- `apps/api/src/users/`
  - `GET /api/me` は、セッションのクッキーキャッシュ（ADR 0005、最大 5 分）ではなく DB からユーザーを読む。表示名を変えた直後でも新しい値を返すためである。
  - `PUT /api/me/favorite-songs` は、曲を `getOrCreateSong` で確定した後、Apple が返した ISRC で重複を確かめる。入力の ISRC が違っても、同じ曲を 2 回選べないようにするためである。
  - `GET /api/users/:publicId` は、利用停止中・退会済みのユーザーを見つからない扱いにする（404）。
- 絵文字は、`Intl.Segmenter` で数えて 1 つの書記素（見た目の 1 文字）であり、絵文字の文字を含むことを API で確かめる。DB では確かめない。

## 検討した他の案

- **Better Auth の `/update-user` で表示名を変える**：理由 1 のとおり、検証の規則が 2 か所に分かれるので、採用しない。
- **お気に入りを 1 件ずつ追加・削除・並び替えする API**：理由 2 のとおり、操作ごとに並び順と件数の確認が必要になるので、採用しない。

## この決定による影響

- お気に入りを 1 件変えるだけでも、画面は一覧全体を送る。最大 10 件なので、送る量は小さい。
- Better Auth を更新したときに、新しく公開される変更用の API がないかを確かめる必要がある。
