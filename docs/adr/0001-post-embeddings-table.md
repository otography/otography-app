# 投稿の埋め込みを posts テーブルとは別の post_embeddings テーブルに保存する

投稿本文の埋め込みベクトルは、posts テーブルの列には置かず、posts と 1 対 1 で対応する post_embeddings テーブルに保存する。埋め込みを posts の列に置くと、投稿を読み出すすべての処理が埋め込みの扱いを考える必要がある。また、埋め込みと投稿本体とでは、作成や更新が起こる時期と理由が異なる。この 2 点が理由である。

## 前提

- 埋め込みの型は F16_BLOB(2048) であり、1 件の大きさは 4,097 バイト（2 バイト × 2,048 次元 ＋ 型を示す 1 バイト）である。
- 埋め込みを使う処理は意味検索である。投稿を画面に表示する処理（タイムライン、プロフィール、投稿の詳細）は埋め込みを使わない。
- 埋め込みは投稿本体とは別に作られる。作成に失敗した投稿の埋め込みは、後でバッチが作る。
- 埋め込みモデルを変えた場合は、すべての埋め込みを作り直す。異なるモデルで作った埋め込み同士は比較できないからである。
- API は Cloudflare Workers で動き、データベース（Turso）にはネットワークを通して接続する。

## 理由

### 1. posts の列に置くと、投稿を読み出すすべての処理が埋め込みの扱いを考える必要がある

- Drizzle の `select()` とリレーショナルクエリは、列を指定しない場合にすべての列を返す。埋め込みが posts の列であると、列の除外を忘れた処理は、表示に使わない約 4KB のデータを投稿 1 件ごとにデータベースから受け取る。投稿 100 件の一覧では約 400KB になる。
- リレーショナルクエリで posts を入れ子にして読み出すと、Drizzle は各列の値を JSON にまとめる。SQLite の JSON は BLOB を値として持てないため、2026-11-16 のローカル検証では `JSON cannot hold BLOB values` というエラーになった。
- 列の除外がすべての処理で守られているかどうかを、型検査で確かめる方法はない。

### 2. 埋め込みと投稿本体とでは、作成や更新が起こる時期と理由が異なる

- 投稿本体は、ユーザーの操作によって作成・削除される。
- 埋め込みは、投稿本体の保存とは別に作成される。作成に失敗した場合はバッチが後で作成し、モデルを変えた場合は全件が作り直される。
- posts の `updated_at` は、行を更新するたびに現在時刻に変わる。埋め込みが posts の列であると、埋め込みを作り直しただけで投稿の `updated_at` が変わる。別のテーブルであれば、投稿の `updated_at` は変わらない。
- 別のテーブルには `model` 列を置くので、作り直す対象を `model` 列の値で探せる。

### 3. 「埋め込みが無い」状態を、NULL ではなく行の有無で表せる

- posts の列であれば、埋め込みが無い投稿は NULL で表す。その場合、ベクトルインデックスを `WHERE embedding IS NOT NULL` 付きの部分インデックスにする必要があった。
- 別のテーブルであれば、埋め込みが無い投稿には行が無い。埋め込みの列は NOT NULL にでき、ベクトルインデックスに条件を付ける必要もない。
- 埋め込みがまだ作られていない投稿は、posts と post_embeddings を LEFT JOIN して探せる。

## 検討した他の案

- **posts の列に置き、読み出す処理で必ず列を除外する（変更前の形）**：理由 1 の除外漏れを防ぐ方法がなく、理由 2 と理由 3 の問題も残るので、採用しない。
- **posts の列に置き、列の型に codec `"blob"` を指定して、入れ子の読み出しのエラーだけを解消する**：エラーは解消するが、約 4KB を余計に受け取る問題と、理由 2 と理由 3 の問題が残るので、採用しない。なお、post_embeddings の列の型にも codec `"blob"` を指定している。投稿と埋め込みをリレーションで一緒に読み出す処理があり得るからである。

## この決定による影響

- 意味検索のクエリは、`vector_top_k('post_embeddings_vector_idx', …)` が返す id を `post_embeddings.rowid` と結合し、その後で posts と結合する。`vector_top_k` が返す id は post_embeddings の rowid であり、投稿の id ではない。
- 投稿が削除または非表示にされたときは、API がその投稿の post_embeddings の行を削除する。投稿の行を物理削除した場合は、外部キーの ON DELETE CASCADE によって post_embeddings の行も削除される。非表示を解除した投稿は、埋め込みを作り直す必要がある。
- 設計ドキュメント（「スキーマ」タブ）は posts に embedding 列と embedding_model 列を置いており、この決定とは異なる。
