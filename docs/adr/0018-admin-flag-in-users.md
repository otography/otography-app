# 管理者は users.is_admin で表し、値は DB の SQL でだけ変える

管理者かどうかは、`users` の `is_admin` 列（真偽値、既定は偽）で表す。この列は API から変えられないようにし、管理者を決めるときは Turso の DB に SQL を実行して変える。管理の API では、管理者かどうかを、セッションのクッキーキャッシュではなく DB から読んで確かめる。管理者は運営者の数人だけであり、管理者を決める画面や仕組みを作るほどの頻度が無いからである。

## 前提

- 設計ドキュメントは、管理者による投稿の削除・非表示とユーザーの停止を、公開時の最小の機能と定めている。誰を管理者とするかは決めていなかった（MUS-66）。
- 管理者は、運営者の数人だけを想定している。管理者を足したり外したりする頻度は低い。
- ログインは Better Auth で行う。Better Auth は、セッションとユーザーの情報を署名付きのクッキーに最大 5 分保存する（docs/adr/0005-session-cookie-cache.md）。

## 理由

### 1. 管理者を DB の列で表す

- 管理者を環境変数（管理者のメールアドレスの一覧など）で表すと、本番と staging の Preview のそれぞれにシークレットを登録する必要がある。また、管理者を変えるたびにデプロイが要る。
- DB の列で表すと、SQL を 1 回実行するだけで管理者を変えられる。リポジトリに個人の情報を書く必要も無い。

### 2. 列は API から変えられないようにする

- Better Auth の `additionalFields` で `input: false` を指定し、ログインや登録の入力からは値を設定できないようにした。
- 自分の情報を変える API（`PATCH /api/me`）は、表示名と自己紹介だけを受け付ける。`is_admin` は受け付けない。

### 3. 管理者かどうかは DB から読む

- セッションのクッキーキャッシュから読むと、管理者を外しても、最大 5 分は管理の API を使えてしまう。
- 管理の API を呼ぶ回数は少ないので、毎回 DB を 1 回読んでも負担は小さい。

## 検討した他の案

- **Better Auth の admin プラグイン（`role` 列）を使う**：利用者の作成・削除や、なりすまし（impersonation）など、使わない機能の API が増える。採用しない。
- **環境変数で管理者のメールアドレスを列挙する**：1. の理由により、採用しない。

## この決定による影響

- 管理者を決めるときは、対象の DB で次の SQL を実行する。`turso db shell <DB 名>` などで実行する。

  ```sql
  update users set is_admin = 1 where public_id = '<公開 ID>';
  ```

- 管理の API（`/api/admin/*`）は、`requireAuth` の後に `requireAdmin` を付ける。管理者でなければ 403 を返す。
- `GET /api/me` は `isAdmin` を返す。画面は、この値で「通報の管理」へのリンクを出す。ただし、権限の確かめは API の側で行う。
- 停止したユーザーのセッションは、停止と同時に消す。ただし、クッキーキャッシュの期限（最大 5 分）までは、そのユーザーの画面が使えることがある。
