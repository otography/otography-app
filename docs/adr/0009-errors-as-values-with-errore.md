# 想定される失敗は、例外ではなく errore の方式で値として返す

API のコードでは、想定される失敗（外部の API の 404 や 429、入力の不正、DB の失敗など）を例外として投げず、`Error | T` の型の値として返す。書き方は errore（https://errore.org）に従う。例外を使うと、関数がどのような失敗を起こすかが型に現れず、呼び出し側が失敗の扱いを書き漏らしても型チェックで見つからないからである。

## 前提

- これから作る API（曲の取得、投稿、お気に入りなど）は、Apple Music API、Turso、Workers AI を呼ぶ。これらの呼び出しは、相手の状態によって失敗する。
- 失敗の種類によって、利用者に返す HTTP のステータスと文言が異なる。たとえば、Apple Music に曲がないときは 404、Apple Music API のレート制限を超えたときは 503 を返す。

## 理由

### 1. 例外では、失敗の種類が関数の型に現れない

- TypeScript の型は、関数が投げる例外を表さない。そのため、呼び出し側が `try`/`catch` を書き忘れても、型チェックは通る。また、`catch` で受け取る値の型は `unknown` であり、どの失敗かを判別するには、呼び出し先の実装を読む必要がある。
- 失敗を戻り値の型（たとえば `AppleSongNotFoundError | AppleMusicRateLimitError | Song`）に含めると、呼び出し側は `instanceof Error` で分岐するまで成功時の値を使えない。失敗の種類は型に列挙されるので、扱いの漏れを型チェックで見つけられる。

### 2. errore は、結果を包む型を持たない

- 失敗を値として返す他のライブラリ（neverthrow の `Result`、Effect）は、成功時の値と失敗を専用の型で包む。そのため、値を取り出す操作（`match`、`map` など）を覚える必要があり、包む型と包まない型の変換がコードのあちこちに入る。
- errore は、戻り値を `Error | T` の共用体型のままにし、`instanceof Error` で型を絞り込む。必要なのは、エラーのクラスを定義する `createTaggedError` と、例外を値に変える `.catch` や `errore.try` だけである。

## 実装

- ドメインのエラーは `errore.createTaggedError` で定義する。メッセージのテンプレートにある `$変数` は、コンストラクターの必須の引数になり、エラーの属性としても読める。
- 例外を投げるライブラリ（`fetch`、Drizzle、`jose`）を呼ぶ箇所でだけ、`.catch((e) => new XxxError({ cause: e }))`（非同期）か `errore.try`（同期）で例外を値に変える。元の例外は `cause` に入れる。
- Hono のハンドラーは、返ってきたエラーの種類ごとに HTTP のステータスと文言を決める。
- 書き方の規則は AGENTS.md の「エラー処理」に書いた。

## 例外のまま残すもの

- 起動時の設定不備（`apps/api/src/env.ts` の `requireEnv`）は、例外のまま残す。必要なシークレットがないと、Worker はどのリクエストにも正しく応答できず、値として返しても呼び出し側にできる処理がないからである。
- また、モジュールの読み込み時に例外が起きると、Cloudflare はアップロード時の確認でその版を拒否する（2026-11-17 に、エラー 10021 で拒否されることを確認した）。そのため、シークレットが足りない版は公開されない。

## 検討した他の案

- **例外（`try`/`catch`）のまま書く**：理由 1 のとおり、失敗の種類が型に現れないので、採用しない。
- **neverthrow や Effect を使う**：理由 2 のとおり、結果を包む型を扱う操作が増えるので、採用しない。

## この決定による影響

- 例外を投げるライブラリを呼ぶたびに、`.catch` か `errore.try` で包む必要がある。
- Better Auth のハンドラー（`/api/auth/*`）は Better Auth が処理するので、この方式の対象外である。
