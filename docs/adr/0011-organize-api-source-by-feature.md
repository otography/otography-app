# API のソースは機能ごとのフォルダに分け、その中をルート、ユースケース、リポジトリに分ける

`apps/api/src` のファイルは、機能（認証、ユーザー、曲など）ごとのフォルダに分けて置く。機能のフォルダの中では、HTTP の入出力を扱うルート（`routes.ts`）、利用者がしたいことを 1 つずつ実装するユースケース（`usecases/`）、その機能のデータを読み書きするリポジトリ（`repository.ts`）に分ける。どの機能にも属さないもの（環境変数の読み込み、DB への接続、外部のサービスの API を呼ぶ処理）は `lib/` に置く。1 つの機能を変更するときに読み書きするファイルを 1 つのフォルダに集め、そのフォルダの中では、ファイルの役割を名前から判断できるようにするためである。

## 前提

- これから、投稿、お気に入り、プロフィール、通報、管理者の操作の API を追加する。
- 1 つのルートは、利用者がしたいこと（ユースケース）の 1 つに対応する。たとえば、`POST /api/posts` は「曲を選んで投稿する」に対応する。
- 1 つのユースケースは、複数の機能のデータを読み書きすることがある。たとえば、「曲を選んで投稿する」と「曲をお気に入りに追加する」は、どちらも、選ばれた曲を `songs` から引き、なければ Apple Music から取得して保存する。
- 外部のサービスの API（Apple Music API など）を呼ぶ処理は、複数の機能が使う。たとえば、Apple Music API は、曲の取得とアーティストの取得の両方で使う。

## 理由

### 1. 層ごとのフォルダにすると、1 つの機能の変更が複数のフォルダにまたがる

- 層ごとのフォルダ（`routes/`、`usecases/`、`repositories/`）を `src/` の直下に作ると、たとえば投稿の API を変更するときに、3 つのフォルダのファイルを開く必要がある。
- 機能ごとのフォルダにすると、変更するファイルは 1 つのフォルダに収まる。機能を追加するときは、フォルダを 1 つ作り、`index.ts` に 1 行を足す。

### 2. 機能のフォルダの中を役割で分けると、ルートとユースケースとリポジトリを別々に変更・テストできる

- ルートは、HTTP の入出力（リクエストの検証、ユースケースの呼び出し、エラーの種類から HTTP のステータスへの変換）だけを扱う。
- ユースケースは、HTTP に依存しない。DB や外部の API を呼ぶ処理を引数で受け取るので、テストでは、それらを差し替えて、ユースケースの手順だけを確かめられる。
- リポジトリは、その機能のテーブルを読み書きする処理をまとめる。複数のユースケースが同じ読み書きをするときは、リポジトリの関数を共有する。たとえば、`songs/repository.ts` の `getOrCreateSong` は、投稿とお気に入りのユースケースが共有する。
- 処理のファイルに、処理の内容ごとの名前（たとえば `find-or-fetch.ts`）を付けると、ファイルが関数 1 つごとに増え、どのファイルがユースケースで、どのファイルがデータの読み書きかを、ファイルを開かずに判断できない。

### 3. ルートを 1 つのファイルに書き続けると、ファイルが機能の数に比例して長くなる

- Hono のドキュメント（「Building a larger application」）は、機能ごとに `new Hono()` でルートを作り、`app.route()` でつなぐ形を示している。
- 各ファイルでメソッドをつなげて書けば、`app.route()` でつないだ後も、`hc` のクライアントが使う型（`AppType`）は推論される。

## 実装

```
src/
  index.ts                       … 各機能のルートを app.route() でつなぐ
  lib/
    env.ts                       … requireEnv
    db.ts                        … Turso への接続
    apple-music/
      token.ts、catalog.ts       … Apple Music API の開発者トークンとカタログの取得
      errors.ts、schemas.ts
  auth/
    auth.ts                      … Better Auth のインスタンス
    session.ts                   … sessionMiddleware、requireAuth
  users/
    routes.ts                    … GET /api/me
    usecases/get-me.ts
    errors.ts、schemas.ts
  songs/
    routes.ts                    … GET /api/music/token
    usecases/issue-music-kit-token.ts
    repository.ts                … getOrCreateSong
    errors.ts
```

- 機能のフォルダには、必要に応じて次のファイルを置く。
  - `routes.ts`：ルート。ユースケースを呼び、返ってきた値やエラーを HTTP の応答に変える。
  - `usecases/<ユースケース名>.ts`：ユースケースを 1 ファイルに 1 つ置く。ファイル名は、利用者がしたいことを動詞から始めて書く（`get-me.ts`、`issue-music-kit-token.ts`、`create-post.ts` など）。DB や外部の API を呼ぶ処理は、引数で受け取る。
  - `repository.ts`：その機能のテーブルを読み書きする処理。
  - `schemas.ts`：zod のスキーマ（API の入出力、外部の API の応答）。
  - `errors.ts`：`errore.createTaggedError` で定義したエラーと、関数が返すエラーの共用体型。
- ルート、ユースケース、リポジトリのファイルには、エラーの定義と zod のスキーマを書かない。処理のファイルを読むときに処理の流れだけを読めるようにするためである。また、ルートがエラーの種類ごとに HTTP のステータスを決めるときや、テストがエラーの種類を確かめるときに、`errors.ts` を読み込めば済むためでもある。
- ユースケースの中身が、1 つの関数を呼ぶだけの場合（`issue-music-kit-token.ts` など）も、ユースケースのファイルに分ける。ルートが呼ぶものを、常にユースケースにそろえるためである。
- 外部のサービスの API を呼ぶ処理は `lib/` に置く。特定の機能のフォルダに置くと、他の機能がその機能のフォルダから読み込むことになるからである。`lib/` の中のフォルダも、`errors.ts` と `schemas.ts` を分ける。
- テストは `apps/api/tests` の下に、`src` と同じフォルダ構成で置く（例：`tests/songs/repository.test.ts`）。
- `/api/auth/*` と `sessionMiddleware` は、すべてのルートの前に適用する必要があるので、`index.ts` に書く。
- `requireAuth` を通った後のハンドラーでは、`c.var.user` と `c.var.session` の型が null を含まない。ルートは、ログイン中のユーザーを null の確認なしでユースケースに渡せる。

## 検討した他の案

- **層ごとのフォルダを `src/` の直下に作る**：理由 1 のとおり、1 つの機能の変更が複数のフォルダにまたがるので、採用しない。
- **処理のファイルに、処理の内容ごとの名前を付ける（`find-or-fetch.ts` など）**：理由 2 のとおり、ファイルの役割を名前から判断できないので、採用しない。
- **中身の少ないユースケースは、ルートに直接書く**：ルートが呼ぶものが、ユースケースの場合とそうでない場合に分かれるので、採用しない。

## この決定による影響

- 他の機能のデータを読み書きするユースケースは、その機能の `repository.ts` を読み込む。たとえば、投稿のユースケースは `songs/repository.ts` の `getOrCreateSong` を読み込む。
- フォルダを移したので、ADR の中のファイルのパスも新しいパスに書き換えた。
