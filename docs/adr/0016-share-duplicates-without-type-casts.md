# 重複したコードは、エラーの型を保てる場合に限り、共通のモジュールにまとめる

`vp run similarity`（similarity-ts）が重複として指摘したコードのうち、手順が同じものは、共通のモジュール（関数）にまとめる。ただし、共通のモジュールは、型キャスト（`as` や `!`）を使わずに、個々のエラーの型が呼び出し側まで残る形にする。この形にできない重複は、まとめずに残す。同じ手順を 1 か所に置けば、変更と確認が 1 か所で済む。一方で、エラーの型が失われると、ルートが失敗の種類ごとに応答を返せなくなり、その誤りを型チェックが見つけられなくなるからである。

## 前提

- API は、想定される失敗を `Error | T` の値として返す（docs/adr/0009-errors-as-values-with-errore.md）。ルートは `errore.matchErrorPartial` で、個々のエラー（`AppleSongNotFoundError` など）を HTTP のステータスと文言に変換する。呼び出し側に届くエラーの型が `Error` だけになると、`matchErrorPartial` に個々のエラーの名前を書けなくなり、型チェックが失敗する。
- 2026-11-17 に `vp run similarity` を実行したところ、関数の重複が 3 組、型の類似が 1 組、コードの重なりが 22 件見つかった。主なものは、曲とアーティストの保存、いいねの付け外し、お気に入りの置き換え、MusicKit の検索である。
- TypeScript は、戻り値の型 `FindError | Row | null` から 2 つの型引数（`FindError` と `Row`）を推論するとき、エラーの型をすべて `Row` の候補にする。`FindError` には候補が残らないので、その型引数は制約の `Error` になる。2026-11-17 に、最小の例で確かめた。

## 理由

### 1. 手順が同じコードを 1 か所にまとめると、変更が 1 か所で済む

- 曲とアーティストの保存は、「INSERT し、主キーが衝突したら、先に保存した別のリクエストの行を読み直す」という手順が同じである。この手順は、誤るとデータの不整合を起こす。2 か所に書くと、片方だけを直すおそれが残る。そこで、`apps/api/src/lib/find-or-create.ts` の `findOrCreate` と `insertOrFindExisting` にまとめた。
- いいねを付ける処理と外す処理は、INSERT か DELETE かの 1 文だけが違い、件数の数え直しと、投稿が見つからないときの扱いは同じである。そこで、ユースケースを `setLike` の 1 つに、クエリを `writeLike` の 1 つにまとめた。
- 同じ考えで、次のコードもまとめた。
  - お気に入りの置き換え：`replaceRows`、`getProfileOfUser`、`decorationOf`
  - MusicKit の検索：`searchCatalog`
  - テストで、呼び出しを記録する偽の関数：テストのライブラリの `vi.fn` に置き換えた

### 2. 共通のモジュールは、型キャストを使わずに、エラーの型を呼び出し側に残す

- 最初の版の `findOrCreate` は、行とエラーを別の型引数で受け取っていた。前提に書いた推論の仕組みにより、エラーの型引数は `Error` になった。その結果、投稿とお気に入りのルートで、`matchErrorPartial` が型チェックを通らなくなった。
- 戻り値の型を `as` で指定すれば、型チェックは通る。しかし、`as` を使うと、型チェックは実際の値と型の食い違いを見つけられなくなる。そのため、この方法は採らない。
- そこで、`find` の戻り値を、行とエラーを分けずに 1 つの型引数（`Found`）で受け取る形にした。この形では、呼び出し側の個々のエラーの型が、そのまま戻り値の型に残る。キャストは要らない。

### 3. 型キャストなしではまとめられない重複は、残す

- お気に入りの曲とアーティストのユースケースには、Apple Music から取得した結果を、エラーと保存する行に分ける短いループが残る（similarity は 86.25% と報告する）。
- このループを共通の関数にすると、2. と同じ推論の問題が起きる。避けるには型キャストが要る。
- 重複を残すと、2 か所を直す手間が増える。型キャストを使うと、型チェックが誤りを見つけられなくなる。前者の害のほうが小さいと判断し、重複を残した。
- また、重複を確かめる時点は、意図して変えてある。曲は、Apple が返した ISRC で確かめるので、取得の後に確かめる。アーティストは、入力の ID で確かめられるので、取得の前に確かめる。

## 検討した他の案

- **型引数は分けたまま、戻り値の型を `as Extract<T, Error>` などで指定する**：型キャストが要る。さらに、呼び出し側の型引数（`FetchError`）が総称のままでは `Exclude<FetchError, Error>` が解決されず、型チェックが通らなかった。採用しない。
- **similarity の指摘をすべて無くす**：2. と 3. の理由により、型キャストが要る。採用しない。
- **重複をまとめず、そのまま残す**：1. の利点が得られない。採用しない。

## この決定による影響

- 新しく重複したコードも、同じ基準で扱う。型キャストを使わずにエラーの型を残せる場合はまとめ、残せない場合はまとめない。
- `lib/find-or-create.ts` の型引数の形を変えるときは、`vp run api#typecheck` で、ルートの `matchErrorPartial` が型チェックを通ることを確かめる。理由は、ファイルの冒頭のコメントにも書いた。
- 3. で残した重複は、`vp run similarity`（閾値 0.85）の結果に出続ける。閾値 0.95 の `vp run similarity:ci` には出ない。どちらのコマンドも、まだ GitHub Actions では実行していない。
