# 投稿の一覧を返すリレーションには、削除・非表示の投稿を除く条件を既定で付ける

`packages/db/src/relations.ts` では、投稿の一覧を返すリレーション（`users.posts` と `songs.posts`）に、「`deleted_at` が NULL であり、かつ `hidden_at` が NULL である」という条件を付ける。条件を付けないリレーションが必要な場合は、`users.allPosts` のように、名前で区別する。条件をリレーションの定義に持たせれば、クエリを書くたびに条件を書く必要が無くなり、書き忘れによって削除・非表示の投稿が表示されることが無くなるからである。

## 前提

- 投稿は、本人が削除すると `deleted_at` が、管理者が非表示にすると `hidden_at` が設定される。行は 90 日後にバッチが物理削除するまで残る。
- 他人に見せる一覧（プロフィール、「曲で探す」）には、削除・非表示の投稿を表示してはならない。
- Drizzle v1 では、リレーションの定義に `where` を書ける（公式ドキュメント「Drizzle relations」の Predefined filters）。2026-11-16 に、削除済み・非表示・通常の投稿を 1 件ずつ作り、条件付きのリレーションが通常の 1 件だけを返すことを確かめた。

## 理由

- 条件が無いリレーションでは、`with: { posts: true }` と書いたクエリはすべての投稿を返す。条件を書き忘れたクエリは、削除・非表示の投稿を表示してしまう。
- 条件をリレーションの定義に持たせると、`with: { posts: true }` と書くだけで条件が付く。条件を書き忘れる余地が無くなる。
- わかりやすい名前（`posts`）のほうに条件を付けたのは、名前を見て選ぶ人が、特に考えずに安全な側を選べるようにするためである。条件を付けない `allPosts` は、名前を見れば「すべて」を返すことが分かる。

## 検討した他の案

- **リレーションには条件を付けず、クエリを書くたびに条件を書く（変更前の形）**：書き忘れを防ぐ方法が無いので、採用しない。
- **条件を付けたリレーションを `visiblePosts` などの別名で足し、`posts` は条件なしのままにする**：`posts` を選んだ人は条件の無い一覧を受け取るので、書き忘れと同じ問題が残る。採用しない。

## この決定による影響

- 本人の投稿履歴や管理画面のように、削除・非表示の投稿をどう扱うかをその場で決める処理は、`users.allPosts` を使い、条件を自分で書く。
- リレーションを使わないクエリ（`select()` で直接 `posts` を読むものや、`vector_top_k` を使う意味検索）には、この条件は付かない。これらのクエリには、引き続き条件を書く。
- 次の 2 つの表には、意図してリレーションを定義していない。
  - `post_ip_logs`：API の応答に含めてはならない表である。リレーションが無ければ、`with` で誤って読み出すことができない。
  - `reports`：使うのは管理画面の API であり、そのときに定義する。通報した人と通報されたユーザーはどちらも `users` を指すので、2 つを区別するための `alias` が要る。
