# ユーザーの publicId は、登録時に作るランダムな 12 文字とし、その後は変えない

`users.public_id`（URL などでユーザーを指すために公開する ID）には、ユーザーの登録時に、英小文字と数字からなるランダムな 12 文字を入れる。この値は、登録した後に変えない。ユーザーが自分で決める ID（ハンドル名）にはしない。この形を選んだ理由は 3 つある。1 つ目は、`public_id` は NOT NULL なので、登録した時点で値が必要なことである。2 つ目は、値を変えなければ、一度共有された URL が使えなくならないことである。3 つ目は、英小文字だけを使えば、大文字と小文字の違いによる混乱が起きないことである。

## 前提

- `users.public_id` は NOT NULL かつ重複不可である。
- 表示名（`users.name`）は、ほかのユーザーと重複してよい（設計ドキュメント）。そのため、ユーザーを一意に指すには `public_id` を使う。
- 登録は Google ログインの初回に Better Auth が行う。登録の時点で、ユーザーが ID を選ぶ画面は無い。

## 理由

### 1. `public_id` は NOT NULL なので、登録した時点で値が必要である

- Better Auth の `additionalFields` の `defaultValue` に関数を指定し、登録のたびにランダムな値を作る。

### 2. 値を変えなければ、一度共有された URL が使えなくならない

- ユーザーが ID を変えられる形では、ID を変えた時点で、古い ID を含む URL が別のユーザーを指すか、どのユーザーも指さなくなる。
- 値を変えない形では、この問題が起きない。また、ID の重複の確認、使えない文字列（予約語など）の管理、他人になりすました ID の確認といった、ID を選ばせるための仕組みが要らない。

### 3. 英小文字だけを使えば、大文字と小文字の違いによる混乱が起きない

- 大文字と小文字を区別すると、見た目が似た 2 つの ID が別のユーザーを指すことがある。また、人が ID を書き写すときに間違えやすい。

## 値の作り方と強さ

- 値は Better Auth の `generateRandomString`（`better-auth/crypto`）で作る。ソース（`@better-auth/utils/random`）を読み、次の 2 点を確かめた。
  - 乱数には `crypto.getRandomValues()` を使う。暗号に使える品質の乱数である。
  - 1 バイトの乱数のうち、文字の種類の数（36）で割り切れない範囲の値（252〜255）を捨てて引き直す。そのため、どの文字も同じ確率で出る。
- nanoid の `customAlphabet` も同じ仕組みで乱数を作る。そのため、nanoid を依存に加えても、乱数の質は変わらない。nanoid は使わない。
- 組み合わせの数は 36 の 12 乗、約 4.7 × 10¹⁸ 通り（約 62 ビット）である。ユーザーが 100 万人いるとき、どこかで 2 つの値が重なる確率は約 1 × 10⁻⁷ である（n² ÷ 2N で概算）。
- 値は連番ではないので、値から登録の順番や登録者の数は分からない。

## 検討した他の案

- **登録時にランダムな値を入れ、後でユーザーが変えられるようにする**：理由 2 のとおり、変えた時点で古い URL が使えなくなり、ID を選ばせるための仕組みも要るので、採用しない。

## この決定による影響

- 値が既存の値と重なった場合は、DB の重複不可の制約によって、その登録だけが失敗する。作り直して再び試す処理は入れていない。上記の確率から、入れる必要は無いと判断した。
- 将来ハンドル名の機能を加える場合は、`public_id` とは別の列にする。`public_id` は変えない。
- 本物の Google ログインで、登録時に値が入ることはまだ確かめていない（2026-11-16 時点）。
